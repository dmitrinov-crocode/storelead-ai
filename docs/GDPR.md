# Обработка персональных данных (задача 4-11)

Инженерная запись решений, а не юридическое заключение. Перед первой реальной рассылкой её нужно
показать юристу: здесь зафиксировано, **что система делает**, чтобы у юриста было что проверять.

Контакты, которые собирает Epic 4, — это персональные данные субъектов из ЕС. Даже рабочий адрес
вида `anna.kowalska@sklep.pl` персонален: он идентифицирует конкретного человека. Ящик `info@`
персональным не является, но отделить одно от другого без разметки нельзя, поэтому весь список
живёт под одним режимом.

## Что именно обрабатывается

| Данные                           | Откуда                                              | Зачем                                      |
| -------------------------------- | --------------------------------------------------- | ------------------------------------------ |
| Имя и роль                       | страницы About / Contact магазина, JSON-LD `Person` | обращение по имени в письме (5-03)         |
| Адрес электронной почты          | `mailto:`, JSON-LD, текст страниц                   | канал связи                                |
| Ссылка на LinkedIn               | разметка самого магазина                            | проверка, что человек действительно оттуда |
| Доказательство (фрагмент текста) | та же страница                                      | проверяемость: откуда взят факт (3-05)     |
| `source`, `source_url`           | вычисляется                                         | тот же аудит происхождения                 |

Не собирается: телефоны, адреса, данные из платных баз (Apollo, Hunter, Snov), содержимое профилей
LinkedIn. Сам LinkedIn не скрапится — берутся только ссылки, которые магазин опубликовал у себя.

## Основание обработки

**Законный интерес (ст. 6(1)(f) GDPR)** — прямой B2B-контакт с торговым предприятием по поводу
проблем его же витрины.

Тест на баланс интересов, зафиксированный в коде:

- обрабатываются только контакты, **опубликованные самим магазином** для деловой связи;
- собирается минимум, нужный для одного письма, — принцип минимизации (ст. 5(1)(c));
- частных лиц в выборке нет: источник — StoreLeads, там только действующие магазины;
- письма не отправляются автоматически, каждое проходит ручное одобрение (Epic 5, Epic 6);
- право возразить работает и исполняется одной командой — см. ниже.

Согласие как основание не подходит: получить его до первого контакта невозможно. Если модель
рассылки изменится (массовая отправка, повторные касания без ответа), баланс интересов надо
пересматривать — это уже за рамками первого этапа.

## Срок хранения

`CONTACT_RETENTION_DAYS`, по умолчанию **180 дней** с момента записи контакта.

Принцип ограничения хранения (ст. 5(1)(e)): лид, которому за полгода никто не написал, цели больше
не имеет, а держать его дальше нечем оправдать.

```bash
npm run pipeline -- contacts purge            # по настроенному сроку
npm run pipeline -- contacts purge --days 90  # разово короче
```

Удаление запускается вручную, а не молча в середине прогона: срок должен применяться осознанно, и
это должно быть видно в логе.

## Право на удаление и право возразить

Ст. 17 и ст. 21. Обе исполняются одной командой:

```bash
npm run pipeline -- contacts forget --email anna@sklep.pl
npm run pipeline -- contacts forget --domain sklep.pl --reason objection
npm run pipeline -- contacts suppressions      # кто просил не писать
npm run pipeline -- contacts allow anna@sklep.pl   # снять подавление
```

**Почему удаление и подавление — одна операция.** Удалить строку недостаточно: следующий
`contact_search` прочитает ту же страницу About и запишет тот же адрес обратно. Поэтому
`contacts forget` одновременно удаляет данные и заносит идентификатор в `contact_suppressions`, а
`saveContacts` отказывается писать всё, что там названо. Проверка стоит **в репозитории, а не в
шаге** — чтобы её нельзя было обойти, добавив новый источник контактов. На это есть тест: после
`forget` повторное сохранение тех же кандидатов даёт `written: 0, suppressed: 1`.

Список подавления намеренно хранит только идентификатор — ни имени, ни текста обращения. Хэш не
используется: адрес нужно сравнивать с тем, что заново нашлось на сайте.

`contacts allow` снимает подавление, но **не восстанавливает контакты** — они удалены. Магазин
попадёт в сбор заново при следующем прогоне.

## Где данные лежат

Локальный SQLite (`data/database.sqlite`) на машине оператора. Наружу не передаются: внешние вызовы
— это StoreLeads (запрос доменов), PageSpeed (URL витрины) и OpenAI (факты аудита для агентов).
Имя и адрес контакта попадут в промпт Epic 5 при генерации письма — это единственная передача
персональных данных третьей стороне, и её нужно отразить в перечне обработчиков.
